## Wifi

If you want to use the Wifi features of this crate, you must have updated the wifi core firmware to at least version `2.0.1`. You
can read instructions for this process [here](https://wiki.seeedstudio.com/Wio-Terminal-Network-Overview/).

`Wifi::connect_to_ap` checks the firmware's association and DHCP results
before returning an IP address. Use `Wifi::connect_to_ap_detailed` to report
the failing operation and firmware status or eRPC error. On the Seeed
firmware, DHCP start waits for an address to be assigned; a fallback address
after a DHCP failure is not treated as a successful connection. A valid DHCP
lease ending in `.80` is still accepted. These calls use blocking eRPC and
have no host-side response timeout.

After an association failure, `Wifi::last_connection_error` retrieves the
firmware's more specific last-error flag. The value is a diagnostic hint and
should be read immediately after the failure; this eRPC is also blocking.

For cooperative executors, call `Wifi::into_async` after initialization and
before enabling the blocking driver's interrupts. This consumes the driver
and returns a task-owned `wifi_async::Client<WifiIo>` and a UART-owning
`WifiInterrupts`. Keep the latter behind an interrupt-safe mutex, call its
`enable` once, and route SERCOM0_0/SERCOM0_2 to `on_tx`/`on_rx`. Do not also use
`wifi_singleton!` for this radio. The separate owners avoid mutable aliasing
between tasks and interrupts.

`Client::rpc` handles partial RX/TX, queue backpressure, frame bounds, CRC and
reply sequences. Supply a `wait` closure that yields and returns `false` at
the overall request deadline. It is called during transmission and reception,
including unrelated callbacks. A timeout, malformed response or cancelled
request poisons the client; reset the radio and initialize fresh queues before
recovery. Complete RPC-specific error responses do not poison it. Existing
blocking APIs and examples are unchanged. The async interrupt handlers latch
RX overflow/UART errors and mask the failing interrupt; the client reports
these as transport errors instead of panicking.

### DMA transport (`wifi-dma`)

By default the UART to the RTL8720 is driven by interrupts: one interrupt per
byte in each direction (`SERCOM0_0` and `SERCOM0_2`). With the `wifi-dma`
feature it is driven by DMA instead:

* received bytes go into a 2 KiB ring by a circular DMA transfer that runs
  for the life of the program, and RPC replies are read from that ring;
* requests are sent with a blocking DMA write;
* no UART interrupt handlers are defined. The only interrupt is `DMAC_0`,
  once per 2 KiB received, to count ring wraps so unread data that gets
  overwritten is reported as an error.

See [docs/wifi_dma.md](docs/wifi_dma.md) for how the transport works.

The interrupt transport fails once another interrupt keeps the CPU busy for
about 50 µs, because the UART's receive buffer holds only two bytes. The DMA
transport keeps working while other interrupts block the CPU, and uses no CPU
time for the transport while waiting. `wifi_bench` measures both; see the
[examples README](examples/README.md).

`wifi-dma` uses DMA channels 0 (receive) and 1 (transmit) and the `DMAC_0`
interrupt (defined by `wifi_singleton!`), and changes the `wifi_init` call
generated by `wifi_singleton!`. The application creates the
DMA controller and passes the two channels in:

```rust
let mut dmac = wio::hal::dmac::DmaController::init(peripherals.dmac, &mut peripherals.pm);
let channels = dmac.split();
let rx_channel = channels.0.init(wio::hal::dmac::PriorityLevel::Lvl3);
let tx_channel = channels.1.init(wio::hal::dmac::PriorityLevel::Lvl0);

disable_interrupts(|cs| unsafe {
    wifi_init(
        cs,
        sets.wifi,
        peripherals.sercom0,
        &mut clocks,
        &mut peripherals.mclk,
        &mut delay,
        rx_channel,
        tx_channel,
    );
    // Required: unmasks DMAC_0 (ring wrap counting).
    WIFI.as_mut().map(|wifi| wifi.enable(cs, &mut core.NVIC));
});
```

`blocking_rpc` and `connect_to_ap` are unchanged.

For the async client, `wifi-dma` replaces `Wifi::into_async` with
`Wifi::init_async`. It takes any two DMA channels and a static
`WifiDmaBuffers`, and returns a `wifi_async::Client<WifiIo<RxId, TxId>>` and a
`WifiControl` (power and fault control). This transport uses no interrupt at
all, not even `DMAC_0`, so its channels can come from a DMA controller that
other code runs in `async` mode: convert them with `Channel::into_blocking()`
before `init`. See [docs/wifi_dma.md](docs/wifi_dma.md#async-client).

On both transports, receive errors and timeouts are returned as RPC errors
instead of panicking: a lost byte, a UART overflow or framing error, a reply
longer than 2 KiB (`ResponseOverrun`), no reply within about 10 s, or a gap of
more than about 10 ms inside a reply. After an error the transport discards
what it has received so the next RPC starts clean.

Note for CI: the workspace builds this board with `cargo build --examples
--all-features` (`crates.json`), which always selects `wifi-dma`, so CI does
not build the interrupt transport. Build it locally with
`cargo build --release --example wifi_connect --example wifi_scan`.
